# Deploying Summit

The web app runs on **Vercel**, and the API and Postgres run on **Render**. The
browser only ever talks to Vercel: Vercel forwards `/api/*` and `/socket.io/*`
to Render (a "rewrite"), so the site is one origin as far as the browser can
tell.

```
browser ──► Vercel (https://<app>.vercel.app)
              ├─ static files: the built web app (apps/web/dist)
              ├─ /api/*        ──► Render: summit-api ──► Render Postgres
              └─ /socket.io/*  ──►   (long-polling; Vercel doesn't proxy WebSockets)
```

## Why the proxy (and what it means for cookies)

The login cookie is `HttpOnly; SameSite=Lax; Secure`:

- **SameSite=Lax:** the browser only sends it with requests to the same
  _site_ it came from (plus clicking a link to it). That blocks most
  cross-site request forgery. Through the proxy, every request goes to the
  Vercel address, so the cookie is always same-site and just works.
- **Secure:** only sent over HTTPS (on in production; `localhost` counts as
  secure in browsers, so local runs still work).
- **The alternative** would be the browser calling `*.onrender.com` directly
  from `*.vercel.app`: a different site, so the cookie would need
  `SameSite=None; Secure` plus CORS. Safari and Firefox block such
  "third-party" cookies by default, so sign-in would silently fail for many
  visitors. See decision 037.

## Environment variables

### API (Render, `apps/server`)

| Variable           | Value                                                 | Notes                                                    |
| ------------------ | ----------------------------------------------------- | -------------------------------------------------------- |
| `NODE_ENV`         | `production`                                          | Turns on Secure cookies and production defaults          |
| `NODE_VERSION`     | `24`                                                  | Render's Node version                                    |
| `DATABASE_URL`     | from the `summit-db` database                         | Filled in by the Blueprint                               |
| `JWT_SECRET`       | generated by Render                                   | Never in the repo; changing it signs everyone out        |
| `TRUST_PROXY_HOPS` | `2`                                                   | Vercel's rewrite + Render's load balancer (for real IPs) |
| `WEB_ORIGIN`       | your Vercel address, e.g. `https://summit.vercel.app` | Live connections from any other origin are refused       |
| `PORT`             | set by Render                                         | Don't set it yourself                                    |
| `BCRYPT_ROUNDS`    | (optional) default `12`                               |                                                          |

### Web (Vercel, `apps/web`)

| Variable                   | Value     | Notes                                                 |
| -------------------------- | --------- | ----------------------------------------------------- |
| `VITE_REALTIME_TRANSPORTS` | `polling` | Vercel's rewrite doesn't carry WebSockets             |
| `VITE_API_URL`             | (empty)   | Empty = same origin, which is what the proxy gives us |

`VITE_` variables are built into the JavaScript, so they're public. Never put
a secret in one.

## First deploy

### 1. Render: the API and database

1. Sign in at [render.com](https://render.com) with GitHub.
2. **New → Blueprint**, pick the `summit` repository. Render reads
   `render.yaml` and proposes `summit-db` (Postgres) and `summit-api` (web
   service).
3. When asked for `WEB_ORIGIN`, enter a placeholder for now
   (`https://example.vercel.app`); you'll set the real one in step 3.
4. Apply. The first build takes a few minutes. Then open
   `https://summit-api.onrender.com/health` (your service's address may
   differ if the name was taken). It should say `{"ok":true}`.

### 2. Vercel: the web app

1. If your Render address isn't `https://summit-api.onrender.com`, change the
   two `destination` addresses in `vercel.json` to yours, commit, and push.
2. Sign in at [vercel.com](https://vercel.com) with GitHub. **Add New →
   Project**, import `summit`.
3. Leave **Root Directory** as the repo root (`vercel.json` sets the install,
   build, and output folder for the workspaces). Set **Node.js Version** to
   24.x in the project settings.
4. Add the environment variable `VITE_REALTIME_TRANSPORTS` = `polling`.
5. Deploy. Note the address, e.g. `https://summit-yourname.vercel.app`.

### 3. Connect them

1. In Render, open `summit-api` → **Environment**, set `WEB_ORIGIN` to the
   exact Vercel address (scheme and host, no trailing path). Render redeploys.
2. Smoke test (below).

Later pushes to `main` redeploy both automatically.

## Smoke test

- [ ] `https://<app>.vercel.app/api/auth/me` answers `401` JSON (the proxy works)
- [ ] Create an account, reload: still signed in (the cookie works)
- [ ] Finish a 1-minute session (set it in Timer settings): history and climb update
- [ ] The stats page loads
- [ ] Two browsers (one private window) join one rope team and finish a session together
- [ ] Sign in with a wrong password 11 times: the 11th is refused, but a
      friend on another network can still sign in (rate limit is per visitor)
- [ ] Install the app (PWA) and open it offline

## Free-tier facts to know

- **The API sleeps** after about 15 minutes without traffic, and the next
  request waits roughly a minute while it wakes. The app is built for this:
  guests start instantly, remembered users carry on offline, and finished
  sessions wait in the outbox.
- **Live rooms are in memory** on one instance, so a sleep, restart, or
  deploy ends running team sessions (decision 029).
- **Free Render Postgres expires** a limited time after creation (30 days at
  the time of writing) unless upgraded. Check Render's current terms.
